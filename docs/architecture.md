# Ritualist architecture

Goal: a multi-platform micro-learning app that stays **under 150 MB RAM**,
boots instantly, works fully offline, and keeps its core engine reusable for
future course modules (V1: Islam).

Measured baseline (Windows release, idle): **136 MB working set**, 25 threads.

## 1. Stack decision

| Option | Verdict | Why |
| --- | --- | --- |
| **Flutter 3.35.3 (chosen)** | native AOT compile, single codebase for Windows/macOS/Linux/Android/iOS, no JS bridge, no web runtime, predictable memory | meets the < 150 MB budget on desktop, ~1/3 the baseline RAM of Electron |
| React Native / Expo | rejected | JS engine + bridge on top of native shell adds baseline memory and a large node_modules/toolchain surface for the same UI |
| Electron / Tauri-webview | rejected | Electron idles at 300+ MB; a webview UI cannot match the frame-perfect path animations cheaply |
| SQLite / drift / sqflite | rejected | the entire user state is one small JSON document (`Progress`); a database engine plus FFI/path_provider dependencies would add megabytes to save kilobytes. Atomic file writes give the same durability without the weight |

### Zero-external-dependency policy

- `app/` depends only on the Flutter SDK and the local engine package.
- `packages/ritualist_engine/` is pure Dart with zero packages (its tests run
  on a hand-rolled harness via `dart run tool/run_tests.dart`).
- `tools/curriculum/` uses only Node built-ins.
- Consequence: `flutter pub get --offline` always succeeds, the dependency
  tree cannot rot, and the app has no network permission needs at all.

The one deliberate exception to "no assets": the bundled Nunito variable
font (~150 KB) - typography is core to the look, and system fallbacks change
per platform.

## 2. Layering

```
┌─────────────────────────────────────────────────────────────┐
│ app/ (Flutter)                                              │
│  screens/  path · lesson · results · profile                │
│  widgets/  path node, MCQ / ordering / matching views,      │
│            feedback panel, chunky button, status bar        │
│  state/    AppState (ChangeNotifier) · LessonController ·   │
│            ContentStore · ProgressStore                     │
└───────────────┬─────────────────────────────────────────────┘
                │ package:ritualist_engine (pure Dart)
┌───────────────▼─────────────────────────────────────────────┐
│  models/    Exercise (sealed) · Lesson · ModuleManifest     │
│  runner/    LessonRunner - the exercise state machine       │
│  session/   SessionBuilder - lesson & spaced-repetition     │
│  srs/       SM-2-lite scheduling                            │
│  progress/  Progress document · applySessionResult · path   │
│  content/   validators (schema + sourcing rules)            │
└───────────────┬─────────────────────────────────────────────┘
                │ JSON assets (generated by tools/curriculum)
┌───────────────▼─────────────────────────────────────────────┐
│ app/assets/modules/islam/module.json  +  units/*.json       │
└─────────────────────────────────────────────────────────────┘
```

The engine is UI-free and tradition-free: it plays any module that matches
the JSON schema, and a different frontend (CLI, watch, web) could reuse it
as-is.

## 3. State management

`ChangeNotifier` + `ListenableBuilder` only - no provider/riverpod/bloc.

- One root `AppState` owns content, progress and game config; `LessonController`
  owns exactly one running session and is created/disposed by the lesson screen.
- The app has one user, one active screen, and small widget trees (the whole
  path is < 50 lightweight widgets), so observer plumbing stays trivial.
- Writes are debounced (600 ms) into a single `ProgressStore.save`; the root
  widget flushes immediately on app pause/detach.

## 4. Persistence

`ProgressStore` has two implementations:

- `MemoryProgressStore` - tests and exotic platforms fallback.
- `FileProgressStore` - one JSON file, atomically replaced (write `.tmp`,
  then rename). Locations without `path_provider`:

  | Platform | Location |
  | --- | --- |
  | Windows | `%APPDATA%\Ritualist\progress.json` |
  | macOS/Linux | `$HOME/.ritualist/progress.json` |
  | Android | app-private `files/` dir (`com.itsjani.ritualist`) |
  | iOS | `$HOME/Documents` (sandbox HOME) |

A corrupt file is treated as "no file" (fresh start) rather than a crash.
The document stores: hearts + regen anchor, streak days as date keys, a
60-day daily-XP ring, per-lesson completion/SRS state. Content and user data
are fully decoupled - updating a module can never corrupt progress.

## 5. Content model

```
module.json    schemaVersion, id, title, tagline, description, disclaimer,
               units[] each with lesson *summaries* only (id/title/count)
units/<u>.json unitId + full lesson bodies (exercises)
```

- Unit files are lazily loaded and cached in memory; only the units the user
  actually touches are parsed (first unit is prefetched after boot).
- Exercise id convention `module.unit.lesson.n` with deterministic display
  shuffles: `fnv1a(id)` seeds an Xorshift PRNG so a step-ordering pool or
  matching column looks different every exercise but identical across restarts.
- The validator (`requireSources: true` for the Islam module) enforces ids,
  option/pair counts, unique texts, and that every exercise has a source +
  explanation before content can ship.

## 6. Game loop (engine rules)

- **Hearts**: max 5, −1 per wrong non-matching answer, regen 1/30 min
  (anchored on the last loss); practice sessions are heart-free and passing
  one restores a heart.
- **Mistakes are re-injected**: a wrong exercise reappears once at the end of
  the session.
- **XP**: lesson base XP + perfect bonus; practice pays `practiceXp` only on a
  pass. Daily goal (10/20/30/50) drives the ring in the status bar.
- **Streak**: date-keyed; `displayStreak` keeps yesterday's streak visible
  until midnight so the flame "survives" a late-night session.
- **SRS**: SM-2-lite per exercise (ease + interval, interval caps at 30 d);
  `SessionBuilder.reviewSession` prefers due lessons, falls back to the
  weakest ones, and samples ≤ 4 exercises per lesson to ≤ 12 total.

## 7. UI/UX mapping

The visual identity is original (jade palette, Nunito, own strings and
dimensions), but the *patterns* follow the REA study in
[rea-duolingo-findings.md](rea-duolingo-findings.md):

- path tree with zigzag offsets, unit bands, START bubble, pulsing current node;
- chunky "lip" buttons: a surface floating 3 px above a darker edge that
  compresses on press (AnimatedPositioned, 70 ms);
- the instant feedback panel: green praise / red correction with solution,
  explanation and source pill, sliding up under the exercise;
- a slim status strip: streak flame, hearts, XP ring towards the daily goal;
- implicit animations only (AnimatedContainer/Switcher/Slide); the single
  repeated ticker is the current node's pulse - no particles, no video.

Performance budget notes: icon-font glyphs instead of images, no blur/no
backdrop filters (zero-blur lip shadows are just offset boxes), scrollable
lists are lazy, and every screen is width-constrained to 520-560 px so desktop
windows render the mobile composition cleanly.

## 8. Testing

- **Engine** (61 tests): runner state machine (mistake re-injection, heart
  failure, abandon), SRS transitions, progress update rules, path unlock
  logic, validator rules, JSON round-trips, and a test that validates the
  *actual shipped Islam module* once it exists on disk.
- **App** (1 widget test): boots the whole app against a fake content store
  and asserts the path screen renders offline. It also regression-guards
  widget lifecycle issues (it caught a real ticker-created-in-dispose bug
  during development).
- `dart run tool/validate_content.dart` gates every content regeneration;
  `node tools/curriculum/build.mjs` is deterministic, so diffs are reviewable.

## 9. Deliberate V1 scope cuts

- Light theme only (halves the color-token surface).
- No audio or sound effects (asset weight + platform quirks).
- No accounts, cloud sync or telemetry - everything local.
- Single visible module (Islam); the module browser arrives when module #2 does.
